# F1 — visible GPU device-loss recovery, 2026-09-26

When the active WebGPU device is lost, including a `destroyed` reason, the game now stops its render scheduler, clears and locks held input, and shows one accessible Reload game dialog. Reload returns to a new ready scene. Intentional render-loop disposal remains silent. The dialog keeps technical error details available and removes background controls from keyboard focus. The implementation follows [Babylon Lite's 1.31.1 device-loss guide](https://github.com/BabylonJS/Babylon-Lite/blob/npm-lite-v1.31.1/docs/lite/architecture/50-device-lost-recovery.md): full-page reload is the supported boundary for this app's PCF/CSM shadow setup.

The focused device-loss and frame-scheduler tests pass (17/17), and the game build passes. In an owned 1280×720 Chromium WebGPU session, `check-device-loss.mjs` passed nine assertions: dialog initially hidden; active `GPUDevice.destroy()` produced one focused Reload action; scheduler terminal; held input cleared; no further frame submission; game rendered before loss; reload returned to ready; no uncaught page errors. The single console error is the deliberately triggered device-loss diagnostic. A reviewed [live loss clip](https://ve.sparkify.dev/wow-clone/ashen-reach/lite1311-f1/2026-09-26-device-loss-motion.mp4) shows movement and dialog appearance. Its timestamped capture encoded to 1280×720, square pixels, rotation 0, 1.25 seconds; VE returned seekable HTTP 206 `video/mp4`, and Chromium played it at matching dimensions. The screencast stops supplying new frames once the GPU is destroyed, so reload behavior is evidenced by the separate live assertion and screenshot, not by an extended recording.
